# امنیت بک‌اند و آکادمی

بازبینی کد و تست‌های محلی: ۲۱ نوامبر ۲۰۲۶. این سند وضعیت کد را توضیح می‌دهد؛ تنظیمات سرویس میزبانی و دیتابیس تولید باید جداگانه بررسی شوند.

## ورود و نشست

- شناسهٔ ایمیل داخلی همیشه با حروف کوچک ساخته می‌شود تا با جست‌وجوی Better Auth سازگار باشد. مهاجرت `0013_normalize_internal_email` فقط حروف آدرس‌های داخلی قدیمی را یکدست می‌کند؛ ایمیل واقعی را تغییر نمی‌دهد. محافظ یک‌بار ثبت ایمیل، فقط همین تبدیلِ آدرس داخلی به حروف کوچک را مجاز می‌کند و بازگرداندن ایمیل تأییدشده به شناسهٔ داخلی همچنان ممنوع است. آزمون `test:email:internal` خطای کد صحیح برای حساب قدیمی و رفع آن پس از مهاجرت را بازتولید می‌کند.

اعلان‌ها نیز نشست، مالکیت داده، کنترل Origin، اعتبارسنجی Zod و محدودیت درخواست مستقل دارند. اشتراک‌های پوش فقط برای سرویس‌های مجاز HTTPS پذیرفته می‌شوند و کلید خصوصی VAPID در سرور می‌ماند. مقصد پس از ورود فقط مسیرهای مجاز امتیاز و دوره است. جزئیات صف، رفع تکرار و آزمون‌ها در [راهنمای اعلان‌ها](STUDENT-NOTIFICATIONS.md) آمده است.

- Better Auth، افزونهٔ username و آداپتر رسمی Drizzle مسئول احراز هویت، هش رمز، اعتبارسنجی نشست و محدودیت درخواست ورود هستند. ثبت‌نام، تغییر مستقیم کاربر، حذف حساب و بازیابی رمز از API عمومی باز نیستند.
- ورود برای هر IP حداکثر ۳ تلاش در ۱۰ ثانیه دارد. علاوه بر آن، هر نام کاربری نرمال‌شده حداکثر ۲۰ تلاش در ۱۰ دقیقه دارد؛ تغییر IP یا بزرگی و کوچکی حروف این سقف را دور نمی‌زند. کلید نام کاربری با HMAC ذخیره می‌شود.
- درخواست محدودشدهٔ HTTP با وضعیت ۴۲۹ و `Retry-After` پاسخ می‌گیرد. خطای نام کاربری ناموجود و رمز نادرست یکسان است.
- محافظ مشترک `security/auth-handler.js` پیش از خواندن بدنهٔ ورود، سقف ۳۰ درخواست در دقیقه برای هر IP اعمال می‌کند؛ JSON خراب و ورودی نامعتبر هم شمرده می‌شوند. مسیرهای خواندن/تمدید نشست و خروج سقف مشترک ۱۸۰ درخواست در دقیقه برای هر IP دارند. این سقف‌ها علاوه بر محدودیت‌های داخلی Better Auth و سقف نام کاربری‌اند. خطای سرویس پاسخ عمومی `503` و `Retry-After` می‌دهد و جزئیات داخلی در پاسخ قرار نمی‌گیرد.
- APIهای اعلان و پوش پیش از بررسی کوکی سقف مشترک ۲۴۰ درخواست در دقیقه برای هر IP دارند؛ پس از احراز هویت، سقف مخصوص کاربر نیز اعمال می‌شود. خواندن اعلان‌ها و تنظیمات پوش ۱۲۰، ثبت خوانده‌شدن ۳۰ و تغییر اشتراک پوش ۱۰ درخواست در دقیقه است. تمام پاسخ‌های محدودشدهٔ این APIها نیز `Retry-After` دارند.
- IP تنها از هدر پراکسیِ مورد اعتماد گرفته، با Zod اعتبارسنجی و با HMAC به کلید محدودکننده تبدیل می‌شود؛ شکل‌های معادل IPv6 یک کلید دارند. IP نامعتبر یا غایب یک سهمیهٔ مشترک دارد و کلید نامحدود نمی‌سازد. تنظیم پراکسی طبق بخش انتشار برای میزبانی خارج از Vercel الزامی است.
- کوکی نشست `HttpOnly` و `SameSite=Lax` است و روی HTTPS صفت `Secure` دارد. نشست هفت روز اعتبار دارد و روزانه تمدید می‌شود؛ تغییر ایمیل به نشست تازه‌تر از ۱۵ دقیقه نیاز دارد. خروج، نشست ذخیره‌شده را هم باطل می‌کند.
- تمدید با `deferSessionRefresh` خود Better Auth انجام می‌شود: رندر سرور و GET وضعیت نشست را می‌خوانند و کلاینت رسمی در صورت نیاز POST به `/api/auth/get-session/` می‌فرستد. به این ترتیب تمدید دیتابیس و کوکی در همان پاسخ قابل نوشتن انجام می‌شوند. POST نیز بررسی Origin و اعتبارسنجی JSON دارد.
- کلاینت رسمی Better Auth هر ۶۰ ثانیه و هنگام بازگشت به پنجره، نشست فعال را بازخوانی می‌کند. انقضای نشست در تب باز هم تشخیص داده می‌شود. درخواست‌ها مهلت ۱۵ ثانیه دارند و ورود خودکار دوباره ارسال نمی‌شود.
- schema ورود و نام کاربری با Zod در `src/lib/validation/sign-in.js` مشترک است و در فرم، API و محدودکننده استفاده می‌شود. نام کاربری نرمال می‌شود؛ فاصله‌های رمز تغییر نمی‌کنند. پس از خطای ورود، نام کاربری حفظ و رمز از فرم پاک می‌شود. هنگام ارسال، فیلدها و دکمه غیرفعال‌اند.
- `BETTER_AUTH_SECRET` حداقل ۳۲ کاراکتر دارد. آدرس احراز هویت باید HTTPS باشد؛ HTTP فقط برای loopback توسعه مجاز است. Zod تنظیمات نامعتبر را بدون چاپ مقدار محرمانه رد می‌کند.

## اکشن‌های نوشتن

`rate-limiter-flexible` با آداپتر اتمیک `RateLimiterDrizzle` محدودیت‌ها را در جدول `student_mutation_limit` نگه می‌دارد. شمارنده بین پردازش‌ها مشترک است و با راه‌اندازی مجدد سرور پاک نمی‌شود.

| عملیات                                                 | سقف برای هر کاربر               |
| ------------------------------------------------------ | ------------------------------- |
| تمام اکشن‌های نوشتن هدف، دوره، امتیاز و پروفایل روی هم | ۴۰ درخواست در دقیقه             |
| تغییر اطلاعات فردی، علاوه بر سقف بالا                  | ۸ درخواست در دقیقه              |
| ارسال کد ثبت ایمیل برای هر حساب                        | ۱ بار در ۲ دقیقه، ۳ بار در ساعت |
| درخواست تأیید کد برای هر حساب                          | ۱۰ بار در ۱۰ دقیقه              |

اکشن‌های React وضعیت `limit` و پیام قابل نمایش به کاربر برمی‌گردانند؛ وضعیت HTTP آن‌ها تابع پروتکل Server Actions است. خرابی ذخیره‌ساز محدودیت، عملیات نوشتن را متوقف می‌کند. اجرای هفتگی، رکوردهای محدودکننده‌ای را که بیش از یک روز از انقضایشان گذشته، نشست‌های منقضی و رکوردهای تأیید منقضی را با ORM پاک می‌کند. نشست‌های فعال و حساب‌های کاربری حذف نمی‌شوند؛ تاریخ انقضای جدول‌های احراز هویت ایندکس دارد.

احراز هویت و نقش روی سرور بررسی می‌شوند. کاربر فقط پروفایل و هدف‌های خودش را تغییر می‌دهد؛ شناسهٔ کاربر از فرم پروفایل پذیرفته نمی‌شود. مدیریت دوره و امتیاز به استاد محدود است و مالکیت دوره در ORM کنترل می‌شود. نام کاربری رزروشدهٔ استاد با فرم شاگرد قابل تصاحب نیست.

## اعتبارسنجی و اندازهٔ ورودی

- ثبت ایمیل با افزونهٔ Email OTP در Better Auth و ارسال با SDK رسمی Resend انجام می‌شود. کد ۴ رقمی، هش‌شده، یک‌بارمصرف و متصل به حساب و آدرس مقصد است؛ ۵ دقیقه اعتبار و ۳ تلاش مجاز دارد. ایمیل و `emailVerified` فقط پس از تأیید کد با API رسمی افزونه تغییر می‌کنند. API تغییر بدون تأیید غیرفعال است و مسیرهای عمومی OTP نیز از allowlist احراز هویت خارج‌اند. قفل ثبت یک‌باره در دیتابیس حفظ شده است.

- schemaهای مشترک Zod در `src/lib/validation/` قرار دارند. شناسه‌های متصل به اکشن، اعداد، متن، ایمیل، نام کاربری، گیت‌هاب و URL روی سرور بررسی می‌شوند.
- فرم‌های دارای کلید تکراری و فیلد فایل به‌جای متن رد می‌شوند. URL منابع باید HTTPS و بدون نام کاربری یا رمز در آدرس باشد. متن سرفصل پیش از تقسیم به خطوط، محدودیت طول دارد.
- اندازهٔ Server Actions حداکثر ۶۴ کیلوبایت است.
- Next.js ممکن است خطای داخلی ۴۱۳ مربوط به حجم اکشن را در پروتکل Server Actions به پاسخ HTTP ۵۰۰ تبدیل کند؛ بدنه همچنان رد می‌شود و ورودی حجیم در پاسخ بازتاب داده نمی‌شود.
- API ورود و خروج فقط JSON می‌پذیرد. `raw-body` حجم واقعی stream را تا ۸ کیلوبایت محدود می‌کند؛ درخواست بدون `Content-Length` هم بررسی می‌شود. JSON خراب، نوع نامعتبر و فیلد اضافی رد می‌شوند.
- همین خواندن محدود JSON در APIهای اعلان و پوش استفاده می‌شود. پارامترهای query با Zod و `parseQuery` بررسی می‌شوند؛ کلید تکراری، فیلد اضافی و مقدار نامعتبر در query نشست و اعلان رد می‌شود. POSTهای احراز هویت و APIهای شاگردان به Origin معتبر نیاز دارند؛ Origin خالی، `null` و دامنهٔ دیگر رد می‌شوند.
- CSRF و بررسی Origin برای API احراز هویت با Better Auth و برای Server Actions با Next.js انجام می‌شوند؛ این کنترل‌ها غیرفعال نشده‌اند.

## هدرها و مرورگر

هدرهای مشترک در `src/lib/security/headers.js` و اتصال آن‌ها در `next.config.mjs` است: CSP، منع framing، `nosniff`، Referrer Policy، محدودیت مجوزهای مرورگر و HSTS در تولید. پاسخ API با `no-store` ارسال می‌شود.

مسیرهای ورود و داشبورد در `src/proxy.js` برای هر درخواست nonce تازه می‌گیرند. اسکریپت inline موجود در HTML باید nonce معتبر داشته باشد و handlerهای inline مجاز نیستند؛ `strict-dynamic` به اسکریپت‌های مورد اعتماد اجازهٔ بارگذاری وابستگی‌هایشان را می‌دهد. صفحات عمومی همچنان استاتیک‌اند و CSP سازگار با اسکریپت‌های inline خود Next.js دارند؛ این سیاست عمومی به اندازهٔ سیاست nonce محدود نیست. `SiteLink` عبور از بخش عمومی به بخش شاگردان و برعکس را با بارگذاری سند جدید انجام می‌دهد تا سیاست بخش مقصد واقعاً روی مرورگر اعمال شود؛ جابه‌جایی داخل هر بخش همچنان با Router انجام می‌شود. استایل inline برای نیازهای فعلی رابط مجاز است و `unsafe-eval` فقط در توسعه فعال می‌شود.

پوستهٔ داشبورد شناسهٔ کاربرِ داده‌های دریافتی از سرور را با نشست کلاینت مقایسه می‌کند. پس از تشخیص تغییر حساب، محتوای قبلی مخفی، مودال‌های باز بسته و داده‌ها دوباره دریافت می‌شوند. تغییر شناسهٔ حساب، state فرم‌های پروفایل را هم بازنشانی می‌کند.

## انتشار

- مهاجرت جدید را پیش از راه‌اندازی نسخه با `npm run db:migrate` اعمال کنید. سرور را پس از تغییر تنظیمات احراز هویت دوباره راه‌اندازی کنید.
- روی Vercel، هدر مدیریت‌شدهٔ `x-vercel-forwarded-for` مبنای IP است. در میزبانی دیگر، پراکسی جلوی Node باید `X-Forwarded-For` ورودی کاربر را حذف و IP معتبر خودش را جایگزین کند؛ پورت Node نباید مستقیم عمومی باشد.
- PostgreSQL تولید با حساب محدود، اتصال رمزگذاری‌شده و دسترسی شبکهٔ محدود تنظیم شود. حساب مهاجرت می‌تواند از حساب اجرای برنامه جدا باشد.
- `CRON_SECRET` حداقل ۳۲ کاراکتر است. مسیر cron راز را با مقایسهٔ زمان ثابت بررسی می‌کند و خطای دیتابیس را به پاسخ عمومی ۵۰۳ تبدیل می‌کند.
- متغیرهای محرمانه در فایل‌های نادیده‌گرفته‌شده یا تنظیمات میزبان نگهداری می‌شوند و نباید پیشوند `NEXT_PUBLIC_` داشته باشند.

## بررسی‌ها

تغییر رمز عبور از صفحهٔ خصوصی پروفایل و endpoint محدودشدهٔ `change-password` انجام می‌شود. Better Auth رمز فعلی را بررسی و رمز جدید را هش می‌کند؛ Zod تکرار رمز جدید و طول مجاز را در کلاینت و سرور کنترل می‌کند. درخواست به نشست معتبر، Origin مجاز و محدودیت تلاش برای همان حساب نیاز دارد. نشست‌های دیگر پس از تغییر موفق با امکانات کتابخانه لغو می‌شوند و رمزها در لاگ ثبت نمی‌شوند. `npm run test:student:password` این مسیر را روی حساب آزمایشی بررسی می‌کند.

بیلد علاوه بر فایل‌ها و سئو، trace تمام مسیرهای خصوصی و APIهای آکادمی را بررسی می‌کند. تست استقرار، وابستگی‌های ثبت‌شده در خروجی Next.js را به محیط موقت بیرون از پروژه منتقل می‌کند و بارگذاری واقعی rate limiter، ORM و درایور PostgreSQL را آنجا اجرا می‌کند؛ بنابراین `node_modules` محلی نمی‌تواند وابستگی جاافتاده را پنهان کند. این تست با `npm run package` و `npm run check` اجرا می‌شود و پیام واقعی ایمیل یا پوش ارسال نمی‌کند.

```sh
npm run lint
npm run format:check
npm run package
npm run test:validation
npm run test:security
npm run test:security:db
npm run test:security:api
npm run test:students
npm run test:academy
npm audit
```

تست‌های دیتابیس به PostgreSQL آزمایشی مستقل با `STUDENT_TEST_DATABASE_URL` و مجوز ساخت دیتابیس نیاز دارند. تست‌ها شامل درخواست chunked حجیم، CSRF، نشست باطل‌شده، جلوگیری از اسکریپت inline در صفحهٔ خصوصی، تلاش ورود از IPهای متفاوت، محدودیت واقعی فرم پروفایل، اجرای هم‌زمان شمارنده‌ها، انقضا و توقف نوشتن هنگام خرابی ذخیره‌ساز هستند. تمدید کوکی و دیتابیس، ردکردن کوکی دست‌کاری‌شده، ویژگی‌های کوکی برای آدرس HTTPS، استقلال نشست‌ها و حفظ نشست هنگام خطای خروج نیز بررسی می‌شوند. تست ویژگی‌های HTTPS روی handler کتابخانه با Request دارای آدرس HTTPS اجرا می‌شود؛ این تست جای بررسی TLS میزبان را نمی‌گیرد.

وابستگی `esbuild` زیرمجموعهٔ ابزار قدیمی `@esbuild-kit/core-utils` با override هدفمند به نسخهٔ اصلاح‌شده ارتقا یافته است. پس از این تغییر، تولید مهاجرت و بیلد بررسی شده‌اند. مهاجرت‌های ORM و فایل‌های lock را همراه کد نگه دارید و بررسی وابستگی‌ها را دوره‌ای تکرار کنید.
