# تسک‌های بعدی: اعلان‌ها و نمایش تغییرات هفتگی

وضعیت: 🟢 تسک‌های ۱۳ تا ۱۸ در ۲۱ نوامبر ۲۰۲۶ پیاده‌سازی و بررسی شدند؛ تسک باز دیگری در این فهرست نیست. تسک ۱۱ طبق درخواست کاربر همچنان لغوشده است. مهاجرت فعلاً فقط روی دیتابیس محلی اجرا شده است. راه‌اندازی پروداکشن در [راهنمای اعلان‌ها](STUDENT-NOTIFICATIONS.md) آمده است.

ادامهٔ [تسک‌های داشبورد](STUDENT-DASHBOARD-TASKS.md)، با شماره‌های ۱۳ تا ۱۸. قواعد فعلی محاسبهٔ امتیاز و رتبه تغییر نمی‌کنند.

## ۱۳. پوش نوتیفیکیشن برای ثبت امتیاز

- [x] وقتی استاد برای شاگرد امتیاز جدید ثبت می‌کند، پوش برای همان شاگرد ارسال شود؛ ثبت در دوره یا بدون دوره و ثبت پیگیری نیز پوشش داده شوند.
- [x] متن نمونه: «امتیاز جدید برای شما ثبت شد»؛ با انتخاب اعلان، صفحهٔ تاریخچهٔ امتیازها باز شود.
- [x] فعال‌سازی پوش با انتخاب شاگرد و اجازهٔ مرورگر انجام شود؛ پشتیبانی‌نشدن یا رد اجازه، ثبت امتیاز و اعلان داخل سایت را متوقف نکند.
- [x] اعلان فقط پس از ذخیرهٔ موفق امتیاز ایجاد شود؛ ارسال ناموفق یا تلاش دوباره، امتیاز یا اعلان تکراری نسازد.
- [x] وضعیت ارسال و تلاش دوباره در ماژول جدا مدیریت شود؛ خطای پوش باعث شکست یا حذف امتیاز ثبت‌شده نشود.

معیار پذیرش: یک امتیاز جدید، یک اعلان برای گیرندهٔ درست بسازد و کاربر دیگر اعلان آن شاگرد را دریافت نکند.

## ۱۴. ایمیل فقط هنگام ثبت امتیاز جدید

- [x] پس از ثبت موفق امتیاز جدید، ایمیل اطلاع‌رسانی برای شاگردی که ایمیل تأییدشده دارد فرستاده شود.
- [x] از اتصال و فرستندهٔ فعلی Resend استفاده شود؛ رمزها و کلیدها فقط در تنظیمات محیط بمانند.
- [x] ایمیل شامل امتیاز، توضیح استاد در صورت وجود و لینک صفحهٔ تاریخچه باشد؛ ارتباط با دوره، در صورت وجود، مشخص شود.
- [x] در اعلان‌های آموزشی، ایمیل فقط برای ثبت امتیاز جدید ارسال شود؛ اختصاص دوره، تغییر هدف، تغییر رتبه و ثبت هفتگی آمار ایمیل نفرستند.
- [x] نبودن ایمیل، تأییدنبودن آن یا شکست ارسال، مانع ثبت امتیاز و اعلان داخل سایت نشود.
- [x] تلاش مجدد، ایمیل تکراری برای همان ثبت ایجاد نکند؛ ویرایش امتیاز قبلی، رویداد «امتیاز جدید» محسوب نشود.

معیار پذیرش: ثبت امتیاز برای شاگرد دارای ایمیل تأییدشده، یک ایمیل ایجاد کند؛ ثبت دوره ایمیلی ایجاد نکند. ایمیل تأیید پروفایل، جریان مستقل فعلی خود را حفظ کند.

## ۱۵. بخش اعلان‌ها در هدر آکادمی

- [x] آیکون اعلان‌ها به هدر آکادمی اضافه شود و تعداد اعلان‌های خوانده‌نشده را نشان دهد.
- [x] با انتخاب آیکون، فهرست اعلان‌های جدید همان کاربر باز شود و در موبایل و دسکتاپ قابل استفاده باشد.
- [x] رویدادهای اولیه شامل «امتیاز جدید برای شما ثبت شد» و «دورهٔ جدید برای شما اضافه شد» باشند؛ اعلان دوره هنگام اختصاص آن به شاگرد ایجاد شود، نه صرفاً ساخت یک دوره در فهرست استاد.
- [x] اعلان خوانده‌شده و خوانده‌نشده قابل تشخیص باشد و وضعیت خواندن در دیتابیس ذخیره شود.
- [x] با ورود به صفحهٔ اعلان‌ها، همهٔ اعلان‌های فعلی همان حساب خوانده‌شده محسوب شوند؛ نیاز به انتخاب تک‌تک اعلان‌ها نباشد و شمارندهٔ هدر به‌روز شود.
- [x] حالت بدون اعلان، بارگذاری و خطای دریافت مشخص باشد؛ فهرست طولانی به‌صورت مرحله‌ای دریافت شود.
- [x] مدل، اعتبارسنجی و دسترسی اعلان‌ها با ORM و اجزای مشترک پیاده‌سازی شوند؛ کاربر فقط اعلان‌های خودش را بخواند یا خوانده‌شده علامت بزند.

معیار پذیرش: اعلان جدید پس از ذخیرهٔ رویداد در هدر گیرنده دیده شود و خوانده‌شدن آن با مراجعهٔ مجدد حفظ شود.

## ۱۶. هدایت اعلان‌ها به صفحهٔ درست

- [x] انتخاب اعلان امتیاز، فقط صفحهٔ «تاریخچهٔ امتیازها» را باز کند؛ شناسه، اسکرول خودکار یا بردر برای ثبت مشخص لازم نیست.
- [x] انتخاب اعلان اختصاص دوره، فقط صفحهٔ «دوره‌ها» را باز کند؛ مشخص‌کردن یک دوره لازم نیست.
- [x] اعلان داخل هدر، پوش و ایمیل امتیاز، از یک روش مشترک برای ساخت مقصد داخلی استفاده کنند.
- [x] اگر نشست منقضی شده، پس از ورود موفق مقصد همان اعلان باز شود؛ مسیر بازگشت فقط مسیر مجاز داخلی باشد.
- [x] مالکیت امتیاز یا دوره روی سرور بررسی شود؛ تغییر لینک، دسترسی به اطلاعات شاگرد دیگر ایجاد نکند.
- [x] حذف امتیاز یا دوره، لینک اعلان را خراب نکند؛ صفحهٔ فهرست به‌شکل معمول نمایش داده شود.

معیار پذیرش: اعلان، صفحهٔ تاریخچهٔ امتیازها یا دوره‌ها را بدون مشخص‌کردن یک مورد باز کند و مقصد پس از ورود حفظ شود.

## ۱۷. نمایش وضعیت هفتگی در سمت چپ کارت‌های KPI

- [x] آیکون صعودی، نزولی یا خنثی دقیقاً در سمت چپ فیزیکی هر کارت قرار بگیرد؛ محل عنوان، مقدار اصلی و متن‌های فعلی تغییر نکند.
- [x] محل آیکون مستقل از جهت نوشتار باشد؛ در فارسی نیز سمت چپ کارت باقی بماند.
- [x] برای صعود، گرادیان سبز از لبهٔ چپ به سمت راست شروع و به‌آرامی در زمینهٔ فعلی محو شود؛ سایهٔ داخلی سبز نیز از همان سمت اعمال شود.
- [x] برای نزول، همان الگو با قرمز و برای وضعیت خنثی، الگوی ملایم با رنگ خنثی توکن‌های سایت استفاده شود.
- [x] شدت گرادیان و سایه با نیومورفیسم inset فعلی هماهنگ باشد و خوانایی عنوان و مقدار را در تم روشن و تاریک کم نکند.
- [x] صعود یا نزول از مقایسه با هفتهٔ قبل گرفته شود؛ کوچک‌ترشدن عدد رتبه به‌معنی صعود است. دادهٔ ناکافی، وضعیت خنثی و مقدار «—» داشته باشد.
- [x] نبود داده با تغییر صفر اشتباه نشود؛ آیکون و توضیح قابل دسترس، مفهوم وضعیت را بدون اتکا به رنگ منتقل کنند.

معیار پذیرش: چهار KPI، بدون جابه‌جایی محتوای فعلی، در موبایل و دسکتاپ آیکون سمت چپ و رنگ وضعیت درست داشته باشند.

## ۱۸. عدد و آیکون تغییر رتبه در جدول رتبه‌بندی

- [x] در ستون تغییر رتبه، تعداد پله‌های جابه‌جایی همراه با آیکون صعودی، نزولی یا خنثی کنار همان عدد نمایش داده شود.
- [x] صعود با رنگ سبز و نزول با قرمز مشخص شود؛ وضعیت خنثی از توکن رنگ خنثی استفاده کند.
- [x] اگر نسبت به هفتهٔ قبل تغییری رخ نداده، عدد صفر همراه با آیکون خنثی نمایش داده شود؛ اگر سابقهٔ مقایسه وجود ندارد، «—» همراه با آیکون خنثی نمایش داده شود.
- [x] عدد و آیکون یک گروه جمع‌وجور باشند و بین دو خط شکسته نشوند؛ اعداد در فارسی، فارسی نمایش داده شوند.
- [x] توضیح کامل «صعود، نزول یا بدون تغییر نسبت به هفتهٔ قبل» برای دسترس‌پذیری باقی بماند و با مقدار عددی یکسان باشد.
- [x] از منطق مشترک تغییرات هفتگی استفاده شود و محاسبهٔ جدا یا تکراری برای جدول نوشته نشود.

معیار پذیرش: برای مثال، به‌جای متن طولانی، عدد «۲» کنار آیکون صعود دیده شود و همان دو پله صعود نسبت به هفتهٔ قبل را بیان کند.

## ترتیب اجرا و قواعد مشترک

- ابتدا رویداد و رکورد اعلان و مقصدهای مشترک آماده شوند؛ سپس پوش و ایمیل به همان رویداد ثبت امتیاز متصل شوند.
- برای هر رویداد، گیرنده و کانال، شناسهٔ یکتا در نظر گرفته شود تا تلاش مجدد اعلان یا ایمیل تکراری نسازد.
- فایل‌ها و ماژول‌ها کوتاه و مسئولیت‌محور باشند؛ از کتابخانه‌های مناسب، اعتبارسنجی مشترک، ORM و توکن‌های طراحی موجود استفاده شود.
- اجرای تست روی دیتابیس جدا انجام شود و تست‌ها ایمیل یا پوش واقعی نفرستند؛ تغییرات دیتابیس پروداکشن مجوز جداگانه می‌خواهند.
- پس از اجرای هر تسک و بررسی معیار پذیرش آن، تیک همان تسک ثبت شود؛ ثبت این سند به‌معنی اجرای قابلیت‌ها نیست.

## بررسی تکمیل تسک‌های ۱۷ و ۱۸

🟢 تست `npm run test:weekly:ui` با دیتابیس جدا، فارسی و انگلیسی، هر دو تم و عرض‌های ۳۶۰ و ۱۴۴۰ اجرا شد. چهار وضعیت صعود، نزول، صفر و نبود سابقه، جای نشانگر در چپ فیزیکی کارت، رنگ و سایهٔ داخلی، عدم هم‌پوشانی و متن جایگزین دسترس‌پذیر بررسی شدند. تست محاسبات هفتگی، ورود، پنل ادمین، بیلد و محدودیت اندازهٔ فایل‌ها نیز پاس شدند.
