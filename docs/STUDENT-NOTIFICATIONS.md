# اعلان‌های آکادمی

تسک‌های ۱۳ تا ۱۶: اعلان داخل هدر برای امتیاز و اختصاص دوره؛ پوش و ایمیل فقط برای امتیاز جدید. ایمیل تأیید پروفایل جریان مستقل قبلی خود را دارد. اعلان برای داده‌های قدیمی ساخته نمی‌شود.

## جریان داده و ساختار

- مدل‌های Drizzle در `src/lib/db/schema/notifications.js` و مهاجرت `0012_student_notifications.sql` قرار دارند: اعلان، اشتراک مرورگر و صف تحویل.
- ثبت امتیاز یا اختصاص دوره و ساخت اعلان در یک تراکنش انجام می‌شوند. خطای تراکنش هیچ اعلان یا صف نیمه‌کاره‌ای باقی نمی‌گذارد؛ کلید یکتای رویداد مانع ایجاد اعلان تکراری برای همان ثبت می‌شود.
- `src/lib/notifications/create.js` فقط برای امتیاز، ایمیل تأییدشده و اشتراک‌های موجود هنگام ثبت را وارد صف می‌کند. ایجاد دوره در فهرست استاد اعلان نمی‌سازد؛ اختصاص دوره به شاگرد اعلان داخل سایت می‌سازد.
- ایمیل امتیاز، توضیحات استاد را نیز در صورت وجود شامل می‌شود. توضیح همان امتیاز با کنترل مالکیت از دیتابیس خوانده و به‌صورت متن ساده فرستاده می‌شود؛ توضیح خالی عنوان جداگانه ایجاد نمی‌کند. متن توضیح به اعلان مرورگر یا خروجی API فهرست اعلان‌ها اضافه نمی‌شود.
- ارسال شبکه پس از commit با `after` انجام می‌شود. خطای ارسال، امتیاز ثبت‌شده را حذف یا ناموفق نمی‌کند. `delivery-worker.js` پیش از ارسال، مالکیت اشتراک و معتبرماندن ایمیل گیرنده را دوباره بررسی می‌کند.
- صف با قفل `SKIP LOCKED`، اجارهٔ دو دقیقه‌ای، شناسهٔ هر تلاش و حداکثر پنج تلاش پردازش می‌شود. قواعد مشترک در `delivery-policy.js` هستند؛ `drain-deliveries.js` دسته‌های ۲۵تایی را تا خالی‌شدن صفِ آماده، سقف ۵۰۰ پیام یا بودجهٔ ۴۵ ثانیه پردازش می‌کند. پیش از شروع دستهٔ بعد، زمان کافی برای یک تلاش کامل کنار گذاشته می‌شود. اکشن ثبت امتیاز، کران و ابزار خط فرمان همگی همین پردازشگر را صدا می‌زنند. تأخیر تلاش‌های صف از یک دقیقه به‌صورت نمایی افزایش می‌یابد. ارسال ایمیل برای خطاهای موقت، دو تلاش مجدد کوتاه نیز دارد.
- ایمیل با کلید idempotency ثابت فرستاده می‌شود؛ تلاش مبهم بیش از ۲۳ ساعت بازپخش نمی‌شود. نمایش پوش در Service Worker با شناسهٔ اعلان و IndexedDB رفع تکرار می‌شود. تحویل شبکه تضمین مطلق «دقیقاً یک بار» ندارد.

## هدر، پوش و مقصد

- `src/features/notifications/` شامل پنجرهٔ Radix Popover، دریافت مرحله‌ای با SWR، نشان خوانده‌نشده و کنترل فعال‌سازی پوش است. درخواست اجازهٔ مرورگر فقط با کلیک خود کاربر انجام می‌شود.
- پنجرهٔ هدر پنج اعلان آخر و لینک «مشاهده همه» را نشان می‌دهد؛ کنترل فعال‌سازی پوش زیر آن قرار دارد و پس از فعال‌شدن پنهان می‌شود. صفحهٔ خصوصی `/academy/students/dashboard/notifications/` فهرست کامل همان حساب را ده‌تایی با «نمایش بیشتر» دریافت می‌کند. نمایش فهرست، ثبت خوانده‌شدن و ساخت مقصد بین صفحه و پنجره مشترک‌اند؛ صفحه از ایندکس خارج است و مقصد آن پس از ورود حفظ می‌شود.
- Service Worker در `public/academy-notifications-sw.js` فقط مسئول اعلان است؛ تصاویر یا پاسخ صفحات را کش نمی‌کند. خروج از حساب، اشتراک همان مرورگر را از حساب جدا می‌کند.
- وجود اشتراک مرورگر به‌تنهایی به‌معنی فعال‌بودن پوش حساب فعلی نیست. `browser-push.js` اشتراک باقی‌مانده را با نام حساب فعلی در سرور همگام می‌کند؛ فعال‌بودن فقط پس از تأیید سرور نشان داده می‌شود. درخواست متعلق به نشست قبلی رد می‌شود؛ خطای همگام‌سازی اشتراک مرورگر را لغو می‌کند تا پوش حساب قبلی روی دستگاه باقی نماند. انتقال اشتراک، کارهای در صفِ حساب قبلی را به حساب جدید منتقل نمی‌کند و اجازهٔ مرورگر دوباره درخواست نمی‌شود.
- با ورود واقعی به صفحهٔ اعلان‌ها، همهٔ اعلان‌های همان حساب تا آخرین شناسهٔ دریافت‌شده خوانده می‌شوند؛ این کار با درخواست تغییردهندهٔ احرازهویت‌شده انجام می‌شود و پیش‌بارگذاری لینک آن را اجرا نمی‌کند. شمارندهٔ هدر و وضعیت فهرست در کش مشترک به‌روز می‌شوند؛ اعلان جدیدتر از این شناسه یا اعلان حساب دیگر تغییر نمی‌کند.
- مقصدها در `src/lib/notifications/targets.js` مشترک‌اند: امتیاز به صفحهٔ تاریخچه و دوره به صفحهٔ دوره‌ها می‌رود. لینک‌ها شناسه و اسکرول خودکار ندارند و موردی با بردر مشخص نمی‌شود. انتخاب هر اعلان به موفقیت درخواست خوانده‌شدن وابسته نیست.
- نشست منقضی‌شده مقصد مجاز را تا پایان ورود حفظ می‌کند. مقصد خارجی و پارامتر اضافی در مسیر بازگشت پذیرفته نمی‌شود؛ مالکیت داده روی سرور کنترل می‌شود.
- APIها نشست، Origin معتبر، سقف درخواست، بدنهٔ محدود و Zod دارند. اشتراک پوش فقط برای میزبان‌های شناخته‌شدهٔ سرویس‌های پوش HTTPS پذیرفته می‌شود؛ کلیدهای آن وارد پاسخ فهرست اعلان‌ها یا لاگ خطا نمی‌شوند.

## تنظیم محیط و استقرار

همهٔ تنظیمات محلی در همان `.env` نادیده‌گرفته‌شدهٔ گیت می‌مانند؛ نمونهٔ بدون رمز در `.env.example` است:

- `DATABASE_URL`: دیتابیس همان محیط؛ آدرس محلی با آدرس پروداکشن جابه‌جا نشود.
- `BETTER_AUTH_URL`: مبدأ اصلی سایت، برای احراز هویت و لینک ایمیل.
- `RESEND_API_KEY` و `RESEND_FROM_EMAIL`: اتصال فعلی ارسال ایمیل.
- `VAPID_PUBLIC_KEY`، `VAPID_PRIVATE_KEY` و `VAPID_SUBJECT`: کلیدهای پوش سرور. کلید خصوصی هرگز با پیشوند عمومی یا در کلاینت قرار نگیرد. تغییر کلیدها نیازمند اشتراک مجدد مرورگرهاست.
- `CRON_SECRET`: رمز مشترک محافظ مسیرهای زمان‌بندی، حداقل ۳۲ کاراکتر.

مهاجرت‌های ۰۰۱۲ و ۰۰۱۳ در ۲۲ نوامبر ۲۰۲۶ با مجوز کاربر، پس از بکاپ و بررسی آرشیو، روی پروداکشن اجرا شدند. ساخت سه جدول اعلان و حفظ تعداد کاربران، حساب‌ها، دوره‌ها و امتیازهای موجود بررسی شد. متغیرهای بالا باید در محیط مقصد تنظیم باشند؛ اعمال مهاجرت به‌تنهایی فعال‌بودن تنظیمات Vercel یا GitHub Actions را تأیید نمی‌کند. پوش در مرورگر سازگار و محیط امن کار می‌کند؛ نبود پشتیبانی یا رد اجازه، اعلان داخل سایت را مختل نمی‌کند.

ارسال معمول بلافاصله پس از ثبت انجام می‌شود. کران روزانهٔ Vercel در ساعت ۰۷:۰۰ UTC فقط مسیر بازیابی پشتیبان است و برای تلاش مجدد ایمیل به‌تنهایی کافی نیست. برای سازگاری با محدودیت پلن Hobby، اجرای مستقل ساعتی در `.github/workflows/student-notifications.yml` آماده شده است؛ دقیقهٔ ۱۷ هر ساعت همان مسیر محافظت‌شده را صدا می‌زند، نه پیاده‌سازی جداگانهٔ ارسال. اجرای هم‌زمان و ارسال تکراری با قفل‌های موجود کنترل می‌شود.

پیش از فعال‌کردن زمان‌بندی، این دو مقدار در تنظیمات Actions مخزن ثبت شوند:

- Repository variable با نام `ACADEMY_URL`: مبدأ HTTPS پروداکشن، مثلاً `https://www.prograin.ir`.
- Repository secret با نام `CRON_SECRET`: همان مقدار تنظیم‌شده در Vercel؛ رمز جدید یا فایل env جدید نیاز نیست.

فایل workflow باید روی شاخهٔ پیش‌فرض قرار بگیرد و Actions فعال باشد. `workflow_dispatch` اجرای دستی را ممکن می‌کند؛ نبود تنظیمات یا پاسخ ناموفق به‌صورت خطای واضح گزارش می‌شود. زمان‌بندی GitHub ممکن است تأخیر داشته باشد و در مخزن عمومیِ بدون فعالیت، پس از ۶۰ روز غیرفعال شود؛ وضعیت اجرای زمان‌بندی باید پایش شود. محدودیت ۲۳ ساعت برای تلاش مبهم ایمیل عمداً حفظ شده تا بیرون از پنجرهٔ idempotency ایمیل تکراری ساخته نشود. فعال‌شدن زمان‌بندی پروداکشن در این مرحله بررسی نشده است. منابع: [محدودیت کران Vercel](https://vercel.com/docs/schedules/cron-jobs/usage-and-pricing)، [زمان‌بندی GitHub](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)، [idempotency در Resend](https://resend.com/docs/dashboard/emails/idempotency-keys).

برای بازیابی دستی صف، `npm run student:notifications` از `DATABASE_URL` جاری استفاده می‌کند و واقعاً پیام می‌فرستد.

## بررسی

تست‌های دیتابیس باید با `STUDENT_TEST_DATABASE_URL` روی PostgreSQL آزمایشی جدا و دارای مجوز ساخت دیتابیس اجرا شوند؛ دیتابیس‌های موقت در پایان حذف می‌شوند.

```sh
npm run test:notifications:events
npm run test:notifications:delivery
npm run test:notifications:drain
npm run test:notifications:scheduler
npm run test:notifications:worker
node scripts/check-award-email-transport.mjs
npm run test:notifications:ui
```

تست‌ها ثبت واقعی فرم، تراکنش، دسترسی، مقصد پس از ورود، خوانده‌شدن، صف هم‌زمان، خطا و رفع تکرار، عرض‌های موبایل و دسکتاپ، دو زبان و دو پوسته را بررسی می‌کنند. ارسال ایمیل و پوش در آزمون‌ها شبیه‌سازی می‌شود و پیامی به کاربران واقعی ارسال نمی‌شود.
